# HNPF 专用 MCP 服务器及插件 — 研究 + 设计报告

> 日期：2026-08-14
> 研究范围：`OpenHacknet-main/`（游戏本体源码）、`Hacknet-Pathfinder-master/`（模组框架源码）、`Hacknet-Pathfinder-docs/`（官方文档）、`联机模组设计/`（已有进程间通信基础设施）

---

## 1. 目标

为 Hacknet + Pathfinder（HNPF）环境打造一个**专用 MCP 服务器**，让 AI（Claude / WorkBuddy / 任意 MCP 宿主）能：

- **查询**游戏运行态：网络地图、节点、文件系统、端口、Flag、任务、玩家状态
- **操作**游戏：执行终端命令、连接节点、读写文件、开端口、跑 exe、存档
- **订阅**事件：连接切换、文件变更、命令执行、任务进度
- 同时保留一条**游戏内可用的同源通道**（`mcp` 终端命令），供人肉/AI 调试

## 2. 研究成果速览

### 2.1 OpenHacknet（游戏本体，C#/FNA）

| 关注点 | 结论 |
|---|---|
| 主循环 | `Game1.Update/Draw`（FNA），`Game1.getSingleton()` 拿单例 |
| 全局入口 | **`OS.currentInstance`**（静态）— 一切外部代码的接入点 |
| 核心状态 | `OS.connectedComp/connectedIP/navigationPath/thisComputer/netMap/terminal/ram`；`NetworkMap.nodes`（List\<Computer\>） |
| Computer | `ip/idName/adminIP/files/users/links/ports/portsOpen/daemons`；`getFolderFromPath(path)` |
| 文件系统 | `FileSystem.root → Folder{files,folders}` → `FileEntry{name,data,size}` |
| 命令链路 | `Terminal.executeLine → OS.execute`（**每命令新线程**）`→ ProgramRunner.ExecuteProgram`（硬编码 if-else）→ `Programs.*` 静态方法 |
| 程序化执行 | `os.runCommand(string)`、`os.launchExecutable(exeName, data, targetPort, args)` |
| 事件/动作 | `RunnableConditionalActions.LoadIntoOS(xml, os)`（SC\*/SA\* XML 条件动作，最通用外部触发通道）、`DelayableActionSystem`、`ActiveMission` |
| **主线程排队** | **`os.delayer.Post(ActionDelayer.NextTick(), action)`** — 外部代码回主线程的官方手段 |
| 存档 | XML，经 `SaveFileManager` 到 `{文档}/My Games/Hacknet/Accounts/` |
| 扩展 | `ExtensionLoader` 读 `Nodes/*.xml`，`Game1.AutoLoadExtensionPath` 可命令行指定 |

**关键结论**：命令天然跑在后台线程，外部直接调 `os.runCommand` 与游戏自身行为一致（安全路径）；直接改状态则务必用 `os.delayer.Post(NextTick(), ...)` 排队到主线程。

### 2.2 Pathfinder（模组框架，BepInEx 5.3.4）

| 关注点 | 结论 |
|---|---|
| 启动链 | `PathfinderPatcher`（Mono.Cecil）公开 Hacknet 全部成员 + 注入 `BepInEx.Hacknet.Entrypoint.Bootstrap()` → `HacknetChainloader` 加载插件 |
| 插件形态 | 继承 `HacknetPlugin`，`[BepInPlugin(guid,name,version)]`；生命周期 `Load() / PostLoad() / Unload()`；自带 `HarmonyInstance/Log/Config` |
| **事件系统** | `EventManager<T>.AddHandler(Action<T>, EventHandlerOptions)`；事件：`OSLoadedEvent`(OS)、`OSUpdateEvent`(每帧)、`CommandExecuteEvent`(命令拦截)、`ExecutableExecuteEvent`、`SaveEvent`(存盘, 可改 XElement) 等 |
| **命令扩展** | `CommandManager.RegisterCommand(name, Action<OS, string[]>, addAutocomplete)` — 注入自定义终端命令；自动补全自动重建 |
| 数据访问 | 直接操作公开化的 Hacknet 类：`Programs.getComputer(os, ip)`、`os.netMap.nodes`、`comp.getFolderFromPath` |
| 端口扩展 | `Pathfinder.Port.ComputerExtensions.AddPort/openPort/GetAllPortStates`；`PortManager.RegisterPort` |
| 特性注册 | `[Command][Event][Daemon][Executable][Action][Condition][Goal][SaveExecutor][ComputerExecutor]`…（AttributeManager IL 注入自动注册） |
| 内容扩展 | `DaemonManager/Daemon`、`ExecutableManager/BaseExecutable`、`Mission.GoalManager`、`Replacements.ContentLoader`（XML 加载器替换） |
| 安装 | DLL 丢 `BepInEx/plugins/`（全局）或 `<扩展>/Plugins`（扩展专属，动态加载/卸载）；存档目录被 patch 到 `./HacknetPathfinder` |
| 依赖 | .NET 4.7.2 / x86；0Harmony 2.5.5、Mono.Cecil、FNA；引用 `HacknetPathfinder.exe + PathfinderAPI.dll + BepInEx.*` |

**关键结论**：Pathfinder 本身就是给"进程内扩展游戏"准备的完整 API 层——MCP Bridge 插件可以全部依赖它，**不需要碰游戏源码**。

### 2.3 现有基础设施（可复用）

- **联机模组管道**（`联机模组设计/01-架构方案.md`）：游戏内 `ServerPlugin`（BepInEx）→ **NamedPipe** → `HacknetServerTerminal` → LiteNetLib UDP 9050。已验证"游戏内插件 + NamedPipe + 主线程事件泵"范式。
- **KernelExtensions（KE 9.x）**：用户自己的扩展框架，Flag 系统、条件动作都在里面——Bridge 未来可暴露 KE 接口。
- **codewhale-tui / deepseek-tui**：AI 终端客户端（`.codewhale/`、`.deepseek/`），与游戏进程无关，仅作参照。

## 3. MCP 架构设计

### 3.1 总体结构（两层桥接）

```
┌────────────────────────────────────────────────────────────────┐
│ AI 宿主 (Claude Desktop / WorkBuddy / Cursor / 任意 MCP 客户端) │
│      │  MCP 协议 (stdio, JSON-RPC 2.0)                          │
│      ▼                                                          │
│  ┌───────────────────────────────┐                             │
│  │  server (Node/TS)    │  ← 本仓库的"服务器"部分       │
│  │  ├─ 工具: get_state/connect/… │                             │
│  │  ├─ 资源: hnpf://network/…    │                             │
│  │  └─ 提示: pentest-guide/…     │                             │
│  └───────────────┬───────────────┘                             │
└──────────────────┼─────────────────────────────────────────────┘
                   │ NamedPipe (本机, 命名管道, 无端口冲突)
┌──────────────────▼─────────────────────────────────────────────┐
│ Hacknet 游戏进程 (FNA)                                         │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  bridge (C# BepInEx 插件) ← 本仓库的"插件"部分   │  │
│  │  ├─ PipeServer: 接收 JSON-RPC 请求                       │  │
│  │  ├─ 主线程泵: OSUpdateEvent 每帧消费请求队列              │  │
│  │  ├─ 执行器: 读=公开化 Hacknet 类 / 写=os.runCommand+API  │  │
│  │  ├─ 事件推送: 状态变化 → 反推给 MCP 服务器                │  │
│  │  └─ 游戏内命令: CommandManager 注册 `mcp`                │  │
│  └──────────────────────────────────────────────────────────┘  │
│  PathfinderAPI (事件/命令/端口/内容注册) + 游戏本体             │
└────────────────────────────────────────────────────────────────┘
```

### 3.2 两个组件

| 组件 | 语言/形态 | 职责 |
|---|---|---|
| **bridge** | C#，BepInEx 插件（DLL 丢 `BepInEx/plugins/`） | 游戏进程内：NamedPipe 服务端、主线程请求泵、状态读写执行器、事件推送、`mcp` 终端命令 |
| **server** | TypeScript，`@modelcontextprotocol/sdk` | 独立进程：对宿主提供标准 MCP（stdio），对游戏用 NamedPipe 客户端连接 bridge |

### 3.3 传输协议（bridge ↔ server）

- **管道**：`\\.\pipe\bridge`（可配置，带进程后缀防多开冲突）
- **消息**：JSON-RPC 2.0 风格，三类型：
  ```json
  // 请求（server → bridge）
  {"id":1,"method":"game.execute_command","params":{"cmd":"connect 10.0.0.2"}}
  // 响应
  {"id":1,"result":{"ok":true,"output":"Connected to 10.0.0.2"}}
  // 事件推送（bridge → server，异步）
  {"event":"node.connected","data":{"ip":"10.0.0.2"}}
  ```
- **握手**：连接后首条消息携带 `token`（可选，`config.json` 配置，防本机其他进程误连）

### 3.4 线程模型（最重要的一条）

```
Pipe 接收线程 ──► ConcurrentQueue<BridgeRequest>（无锁入队）
                    │
OSUpdateEvent 每帧 ──► Dequeue 全部 ──► 执行器（游戏主线程内）
                    │                          │
                    └── 结果通过 ConcurrentQueue 写回 ──► Pipe 发送线程
```

- **所有游戏对象访问都在主线程**（`OSUpdateEvent` 回调里），杜绝竞态
- **读操作**也统一走主线程（游戏内 List 无锁读取不保证安全，宁慢勿崩）
- **事件推送**：bridge 每帧比对 `os.connectedComp.ip / navigationPath` 快照，变化即推事件（不需要 Harmony patch `connect`，省事且不会漏）

| 提示 | 场景 |
|---|---|
| `pentest-guide {targetIp}` | 给定目标，输出渗透路径（先侦察→端口→提权） |
| `mission-debug` | 调试任务 XML：检查 goal 条件、SA 动作序列 |

### 3.8 安全边界

- NamedPipe 默认仅本机进程可连；握手 token 防止误连（`config.json` 里可选）
- **只读模式**：`"readOnly": true` 时 bridge 拒绝全部写操作，适合观摩/审计场景
- 命令白名单/黑名单：`allowedCommands` / `blockedCommands`（如默认拦 `rm` 类、`killall`）
- 频率限制：请求队列每帧最多执行 N 条，防 AI 刷爆主线程导致掉帧

## 4. 关键代码骨架

### 4.1 Bridge 插件（C#）核心

```csharp
[BepInPlugin("com.hnpf.mcpbridge", "HNPF-MCP-Bridge", "0.1.0")]
public class MCPBridgePlugin : HacknetPlugin
{
    private static ConcurrentQueue<PendingRequest> _inbox = new();
    private static ConcurrentQueue<string> _outbox = new();
    private static NamedPipeServerStream _pipe;
    private static string _lastIp; private static List<int> _lastPath;
    private static readonly bool ReadOnly = Config.Value("ReadOnly", false);

    public override bool Load()
    {
        // 1. NamedPipe 服务线程（只做收发，不改游戏状态）
        Task.Run(StartPipeServer);
        // 2. 每帧主线程泵：消费请求、执行、检测事件
        EventManager<OSUpdateEvent>.AddHandler(OnUpdate);
        // 3. 游戏内命令：mcp ping / mcp state / mcp exec <cmd>
        CommandManager.RegisterCommand("mcp", (os, args) => os.write("mcp bridge active"));
        EventManager<OSLoadedEvent>.AddHandler(e => Push("game.loaded", new { }));
        EventManager<SaveEvent>.AddHandler(e => Push("game.saved", new { e.Filename }));
        return true;
    }

    private static void OnUpdate(OSUpdateEvent e)
    {
        while (_inbox.TryDequeue(out var req))
            _outbox.Enqueue(ExecuteOnMainThread(req));   // 主线程执行
        // 事件检测：连接切换
        var ip = e.OS.connectedComp?.ip;
        if (ip != _lastIp) { Push("node." + (ip==null?"disconnected":"connected"), new { ip }); _lastIp = ip; }
    }

    private static string ExecuteOnMainThread(PendingRequest req)
    {
        if (ReadOnly && req.Method.StartsWith("game.")) return Err("read-only mode");
        return req.Method switch
        {
            "game.execute_command" => ExecCommand(req.Params.cmd),
            "state.get"            => Json(OS.currentInstance),          // 序列化公开化对象
            "network.map"          => Json(OS.currentInstance.netMap.nodes),
            "fs.list"              => Json(GetComp(req.Params.ip).files),
            "fs.read"              => ReadFile(req.Params.ip, req.Params.path),
            _ => Err($"unknown method {req.Method}"),
        };
    }
}
```

### 4.2 MCP 服务器（TypeScript）核心

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { NamedPipeClient } from "./pipe.js";   // net.connect('\\\\.\\pipe\\bridge')

const server = new McpServer({ name: "hnpf-mcp", version: "0.1.0" });

server.tool("get_state", "玩家当前状态", {}, async () => ({
  content: [{ type: "text", text: JSON.stringify(await bridge.call("state.get")) }]
}));

server.tool("get_computer", "查询节点 {ip}", { ip: z.string() }, async ({ ip }) => ({
  content: [{ type: "text", text: JSON.stringify(await bridge.call("computer.get", { ip })) }]
}));

server.tool("execute_command", "执行游戏内命令 {cmd}", { cmd: z.string() }, async ({ cmd }) => ({

  contents: [{ uri: "hnpf://network", text: JSON.stringify(await bridge.call("network.map")) }]

await server.connect(new StdioServerTransport());
```

## 6. 落地注意点

1. **编译环境**：Bridge 引用 `HacknetPathfinder.exe + PathfinderAPI.dll + BepInEx.Core/Hacknet.dll + FNA.dll`（.NET 4.7.2 / x86），项目文件可照抄 `ExampleMod.csproj`
2. **NamedPipe 命名冲突**：多开时 bridge **自动改名** `{name}-{pid}`（监听失败时，EffectivePipeName 可查，ping 返回 pipe）；server 用 `pipe_probe` 工具探测各管道在线状态、`HNPF_PIPE` 指定目标实例
3. **序列化**：游戏对象大量 internal 循环引用，手写 DTO 投影（如 `{ip, name, ports, links}`），别直接 `JsonConvert(Computer)`，会炸
4. **与联机模组共存**：两者管道/端口完全独立（本方案 NamedPipe vs 联机 LiteNetLib UDP 9050），可同时启用；联机 ServerPlugin 的 `EVENT:TYPE:data` 协议风格可借鉴
5. **掉落场景**：游戏未启动时 server 应返回清晰错误并轮询重连；AI 侧提示词里注明"先启动游戏再提问"

## 7. 与 HacknetHotReplace 的对比

工作区里的 `HacknetHotReplace-master` 已经实现了"游戏外部控制服务器"，必须说清楚差异与关系。

### 7.1 HotReplace 是什么

| 项 | 内容 |
|---|---|
| 定位 | **模组开发者调试工具**：热重载 XML 内容（Computer/Mission/Action/Faction/Theme/People）、动态执行 Action、打印 OS/Computer 状态、定位绘制调用栈 |
| 架构 | 游戏内插件（依赖 Pathfinder）作 UDP 服务端（8000+ 自动找端口，写入注册表 `HotReplaceServerPort` 公布）；`Game1.Update` Harmony Postfix 里消费消息队列（**主线程处理**）；`SingleThreadSynchronizationContext` |
| 协议 | **自定义 XML**：`<Command><CommandType/><MsgGuid/><Payload/></Command>`，UDP 无连接，响应重试 3 次 |
| 可扩展 | `RegisterMessageHandler(IMessageHandler)` 可插拔处理器（`SupportMsgType` + `HandleMessage`） |
| 泛化能力 | **`ExecuteActionMsgHandler` 用 `Pathfinder.Replacements.ActionsLoader.ReadAction(xml)` 解析任意 SA 动作并 `Trigger(OS.currentInstance)`** —— 已经验证了"泛化执行模组级动作"这条路 |
| 状态访问 | `PrintOsMsgHandler` / `PrintComputerMsgHandler` 打印文本信息 |
| 安全 | 无认证，UDP 谁都能发 |

### 7.2 与 HNPF-MCP 的差异

| 维度 | HacknetHotReplace | HNPF-MCP |
|---|---|---|
| 服务对象 | 人肉开发者 / 调试脚本 | **AI 代理**（标准 MCP 宿主开箱即用） |
| 协议 | 自定义 XML + UDP（动态端口、不可靠、需查注册表） | JSON-RPC 2.0 + NamedPipe/TCP（可靠流式、固定管道名、握手 token） |
| 消息模型 | 纯请求-响应 | 请求-响应 + **事件订阅推送**（AI 实时感知游戏变化） |
| 工具发现 | 固定 13 个 Handler，客户端须知道类型名 | MCP 标准 tools/list + 描述，AI 自动发现 |
| 结果形态 | 原始 XML payload | 结构化 JSON + 人类可读文本（DTO 投影） |
| 状态快照 | 打印文本 | 结构化资源 `hnpf://network` 等 |
| 安全边界 | 无 | 只读模式 / 白名单 / token / 限频 |
| 数据来源 | 游戏本体 + Pathfinder | 同左 + **模组能力抽象层**（见下） |

**结论：HotReplace 是"模组开发者手上的热重载遥控器"，HNPF-MCP 是"AI 的游戏操作系统接口"。二者不冲突，可共存**——Bridge 甚至可以直接复用 HotReplace 已验证的技术点：`Game1.Update` 主线程队列消费、`ActionsLoader.ReadAction` 泛化执行。

## 8. 模组级别：要不要每个模组写一套 MCP？

**不需要。** 核心洞察：模组与 MCP 之间不需要"每模组一框架"，只需要**一层能力抽象 + 注册发现机制**，分三层递进：

### 8.1 第一层：游戏通用能力（覆盖 90% 场景，零模组代码）

无论什么模组，以下能力来自游戏本体，**一次搭建、所有模组通用**：
- 网络/节点/文件系统/端口/Flag/任务/终端命令（get_state / list_files / execute_command / open_port ...）

任何模组的自定义终端命令（经 `CommandManager.RegisterCommand` 注册的）都会**自动出现在 `execute_command` 的可达范围内**——这是最便宜的一条泛化通道。

### 8.2 第二层：Pathfinder 统一注册表泛化（关键设计，几乎不用写代码）

Pathfinder 本身就是模组能力的**统一注册表**：

| Pathfinder 注册机制 | 模组用它暴露什么 | Bridge 泛化调用方式 |
|---|---|---|
| `CommandManager.RegisterCommand` | 自定义终端命令 | `execute_command` 直接可达（零成本） |
| `ActionManager.RegisterAction<T>(xmlName)` | 自定义 SA 动作类型 | `run_action {xml}` → `ActionsLoader.ReadAction(xml).Trigger(os)`（HotReplace 已验证） |
| `ConditionManager.RegisterCondition<T>` | 自定义条件 | `run_action` 内嵌条件一并解析 |
| `DaemonManager.RegisterDaemon<T>` | 自定义守护进程 | 读 `computer.daemons` 泛化序列化 |
| `ContentLoader.RegisterExecutor` | 自定义 XML 节点类型 | `get_computer` 投影时兼容 |

**Bridge 加一个"反射发现"（P2）**：扫描已加载插件程序集的 `[Command]` / `[Action]` / `[Daemon]` 特性（AttributeManager 已收集），自动生成对应 MCP 工具的描述与参数 schema。这样：
> **模组作者只需要按 Pathfinder 惯例注册能力，MCP 工具自动出现——模组一行 MCP 代码都不用写。**

### 8.3 第三层：模组专属适配器（可选，仅复杂模组需要）

只有模组有**独有数据结构/独有交互**（例如 KernelExtensions 的专属界面状态、联机模组的服务器面板）时，才需要轻量适配：

```csharp
// 模组内几十行：把已有 API 包装成 MCP 工具，Bridge 自动装配
[McpTool("ke.get_extensions", "列出已加载的 KE 扩展")]
public static string KeGetExtensions() => Json(KE_Api.GetLoaded());

[McpTool("ke.set_flag", "设置 KE Flag")]
public static string KeSetFlag(string name) => KE_Api.SetFlag(name);
```

Bridge 启动时反射扫描 `IMcpModule` 或 `[McpTool]` 特性自动装配——**是"注册几个工具"，不是"写一套 MCP 框架"**。对比：写一套完整 MCP 框架 = 实现协议/传输/工具发现/安全，约 1000+ 行；写一个适配器 = 十几行标注 + 转发已有 API。

### 8.4 决策树（给未来的模组作者）

```
模组要暴露能力给 AI？
├─ 是游戏本体功能 / 自定义终端命令 → 什么都不用做（第一、二层自动覆盖）
├─ 是 SA 动作 / 条件 / Daemon → 按 Pathfinder 惯例注册（第二层自动覆盖）
└─ 是独有的复杂状态/交互 → 写一个 [McpTool] 适配器类（第三层，十几行）
```

**一句话：MCP 框架只写一次（本方案），模组按 Pathfinder 惯例注册能力，复杂模组补一个十几行的适配器。**

### 8.5 以 KernelExtensions（KE）为例：哪些需要、哪些不需要

KE 的注册模式（`KernelExtensions.cs` Load()）恰好完美演示了三层抽象——**它绝大多数能力已经进了 Pathfinder 注册表，自动吃到第二层泛化**。

#### ✅ 不需要写适配器（自动覆盖）

| KE 能力 | 覆盖层 | 对应的 MCP 工具 |
|---|---|---|
| 22 个 Action：`TerminalWrite/TerminalType/PlaySound/PhaseSwiftScene/Init/Stop/FadeOut/Music/BlockNode/UnblockNode/SetNodeIcon/SwitchToThemeKeepLayout/FailTrial/LaunchVMAttack/RenameNode/Hide-AircraftOverlay...` | 第二层（`ActionManager.RegisterAction`） | `run_action {xml}` 泛化执行 + 反射发现自动生成 schema |
| 4 个 Executable：`#CUSTOMTRIAL#/#PHASESWIFT#/#EFFECTS#/#WPTEST#` | 第二层（`ExecutableManager`） | `launch_exe` |
| `FlightDaemon` | 第二层（`DaemonManager`） | `get_computer` 泛化序列化 daemons |
| `CustomTrialSaveExecutor/PhaseSwiftSaveExecutor`（存档读写） | 第二层（`SaveLoader.RegisterExecutor`） | `save_game/load_game` 天然兼容 |
| **Flag 机制**：`PhaseSwift_*`、`Kernel_VMInfected_*`、`Kernel_VMGuideRead_*`...（KE 大量靠 Flag 驱动场景） | 第一层（游戏通用） | `get_flags/set_flag/clear_flag` —— AI 查/设 Flag 即可驱动 KE 剧本 |
| Harmony Patch 全局行为：MusicManager 压制、IRC 日志、滚动可视化缓冲 | 无需暴露 | 自动生效的修改，AI 不需要调用 |
| `OSLoadedEvent/SaveEvent` 订阅 | 第二层（`EventManager`） | 事件流自动推送 |

**关键洞察**：KE 设计时选了 Pathfinder 惯例（Action/Executable/Daemon/SaveExecutor），所以它"天然 MCP-ready"——Bridge 上线后这些能力零成本可用。

#### 🟡 需要写适配器（第三层，KE 独有内存态）

只有 **KE 的运行时内存状态** 游戏常规对象看不到，需要几十行 `[McpTool]`：

```csharp
public static class KeMcpAdapter
{
    // PhaseSwift 运行时状态：IsRunning/场景/音乐相位/发现节点/黑名单
    [McpTool("ke.phaseswift.state", "PhaseSwift 运行时状态")]
    public static string PhaseSwiftState() => Json(new {
        running = PhaseSwiftManager.IsRunning,
        scene = PhaseSwiftManager.CurrentScene,
        musicPhase = PhaseSwiftManager.CurrentMusicPhase,
        theme = PhaseSwiftManager.DefaultTheme,
        discovered = PhaseSwiftManager.GetSceneDiscoveredNodes(),
        blocked    = PhaseSwiftManager.GetRuntimeBlockedNodes(),
    });

    // CustomTrial 当前试炼
    [McpTool("ke.customtrial.state", "当前试炼配置与已删节点")]
    public static string CustomTrialState() => Json(new {
        config = CustomTrialExe.CurrentInstance?.CurrentConfigName,
        deletedNodes = CustomTrialExe.CurrentInstance?.GetDeletedNodeIndices(),
    });

    // VM 感染配置
    [McpTool("ke.vm.state", "VM 感染模式与检查条件")]
    public static string VmState() => Json(VMInfectionManager.CurrentConfig);

    // KE-Config.xml
    [McpTool("ke.config.get", "读取 KE 配置")]
    public static string KeConfig() => Json(new {
        debug = KEConfigLoader.Debug,
        skipVanillaIRCLogs = KEConfigLoader.SkipVanillaIRCLogs,
        customImages = KEConfigLoader.CustomImages,
    });
}
```

（`KELog` 统一日志则直接接入 Bridge 的日志通道，连适配器都省了。）

**结论（KE 实例）**：9.x 的 22 个已完成功能里，**约 20 个零代码自动覆盖**；只有 4~5 个（PhaseSwift 内存态、CustomTrial 实例、VM 配置、KE-Config）写一个 40 行适配器类。**不需要每个功能写 MCP，更不需要每模组写框架。**
